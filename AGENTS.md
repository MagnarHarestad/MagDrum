# MagDrum project instructions

- The canonical project directory is `C:\Users\Magnar\GitHub\MagDrum`.
- Keep project changes in this repository; do not use the obsolete `MagDrumVST` directory.
- **Plugin UX preference:** Keep each view focused and minimize permanent buttons. Aim for one obvious primary action per workflow; combine related actions or states when their relationship is clear, and place less frequent commands in contextual menus, inline controls or compact lists. Use sliders for continuous choices and searchable/filterable lists for many choices instead of growing toolbars. Prefer progressive disclosure and controls placed beside the content they affect. Keep essential state and primary navigation visible; every non-obvious gesture must have a visible cue or tooltip, and related functions must remain easy to discover. Before adding a control, check whether the same task can be completed more directly through the selected item, a list, a drag gesture or an existing control without making the action hard to find.
- When the user asks to complete and publish project work, commit the finished changes and create the corresponding GitHub release/site update as part of the task.
- **Headless-first acceptance (standing preference):** For Windows/Cubase work, run automated background and offscreen acceptance checks first: Release CTest, Steinberg VST3 validation, isolated installed-package state restore and MIDI 0–127 rendering, and offscreen UI rendering. Continue implementation and release preparation without waiting for the user to run tests when those checks cover the requirement. Never start Cubase or open interactive windows unless the user explicitly asks. Real Cubase-only observations such as audio-device output, project save/reopen inside Cubase, and host-specific visual behavior must remain honestly labeled unverified, but do not stall independent work or mark the project blocked solely to await a user test; list those as optional manual follow-up.
- **Third-party VST scan isolation:** Routine automated acceptance must use synthetic plugin fixtures and must not scan machine-installed commercial VSTs. Never set `MAGDRUM_ALLOW_LIVE_VST_SCAN` from a build or CTest workflow. Run a real inventory scan only for a specific user-requested diagnostic, in a separate isolated data directory and at below-normal priority; record any plugin crash as an unresolved compatibility issue, not a passing scan.
- **CPU-aware development batching (standing preference):** Group related changes into a coherent feature or acceptance milestone before starting a full Release build. During implementation, prefer source review, fast incremental Debug builds and focused checks; run the full Release tests, validators and packaging once at the end of the batch. Do not run build trees concurrently. Use at most two build workers by default so the workstation remains responsive; raise parallelism only when the user explicitly approves or the computer is confirmed idle.
- The standard Windows system-wide VST3 location is `C:\Program Files\Common Files\VST3\MagDrum.vst3`. For the current no-UAC Cubase test flow, install per-user at `%LOCALAPPDATA%\Programs\Common\VST3\MagDrum.vst3`; only use the system-wide path for an explicitly requested elevated install.
- Keep only the current `MagDrum.vst3` in Cubase's scanned VST3 folders. Preserve old bundles under `%LOCALAPPDATA%\MagDrum\VST3-backups` (or `%ProgramData%\MagDrum\VST3-backups` for all-users installs), never beside the active plug-in where Cubase can index them as duplicate versions.
- **Platform pause (standing instruction; check this before every task): Linux and macOS are paused indefinitely. Do not start, continue, schedule, or spend time on Linux/macOS builds, tests, packaging, publishing, CI, install work, documentation, or roadmap implementation. Do not include them in active plans or run cross-platform commands that act on them. Work only on Windows x64/Cubase. Generic requests such as “continue”, “finish”, or “complete the roadmap” do not resume Linux or macOS. Resume either platform only after the user explicitly asks to resume that platform. This rule overrides the roadmap and all generic cross-platform guidance.
- Do not update Linux/macOS documentation or build configuration merely to restate this pause; leave historical platform material untouched until the user explicitly asks to resume those platforms.

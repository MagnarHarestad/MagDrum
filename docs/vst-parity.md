# Standalone-to-VST functionality parity

The VST is intended to expose the MagDrum workflows from inside Cubase. This checklist tracks parity without claiming that the standalone app and an instrument plug-in have identical host responsibilities.

| Standalone workflow | VST status | VST implementation target |
| --- | --- | --- |
| Recursive sample-folder scan, file analysis, cancellation, resume, scan history | Implemented on Windows x64 | The VST scans in a background worker, shares the same database, reports progress and scan results, exposes scan history, and can scan detected default Native Instruments (including the shared Public Documents content root), Spectrasonics/STEAM and Steinberg/Cubase 15 VST Sound and Media locations, plus legacy Steinberg content under per-user Roaming AppData. WAV/AIFF/FLAC audio is indexed. The scan reports Steinberg VST Sound containers and Kontakt NCW files that it cannot decode and guides users to the Plugin Scanner to capture sounds from installed instruments. |
| Find and import drum MIDI patterns from installed default libraries | Implemented on Windows x64 | The default-library scan searches the detected folders for drum-related `.mid`/`.midi` files. The sequencer lists the first 200 results and imports the selected pattern using the active mapping profile. Focused fixtures cover extension case, relevance filtering, result limits and cancellation. |
| Sample search, category/source/kit filters, feature bands, confidence review, sorting and MIDI-note assignment display | Implemented | The VST exposes the standalone browser filters, sort options and paged results. Each sample row also lists the drum-machine MIDI note and velocity ranges where that sample is assigned. SQLite queries are debounced and run on a background worker so large-library filtering does not block the editor. |
| Sample audition, waveform, category/tag edits, source-kit access, sample comparison | Partial on Windows | Preview decoding, sample assignment and project sample restoration decode in cancellable workers so large files do not block Cubase's editor thread. The Sample Library and comparison window can stop the current preview. The open pad waveform and layer summary refresh when project samples finish restoring. Category and tag editing, two-file waveform comparison with per-sample A/B audition, and captured-sample source/kit/MIDI metadata are in the VST. The open comparison window updates its Preview/Stop labels, waveform text and title when the language changes; the .197 Release smoke test checks controls and title in both open comparison and MIDI-event windows in all eight languages, and checks that installed-library drum-MIDI search cancellation can be requested from the VST. The VST can launch a separate MagDrum helper with the selected sample's source instrument and saved kit; that helper reopens the instrument editor. Cubase audio and visual interaction remain part of the host acceptance pass. |
| Exact and perceptual duplicate lookup, similarity candidates | Implemented | The Sample tools menu reports exact duplicates, acoustic-similarity and perceptual near-duplicate candidates. |
| Plugin-instrument discovery, presets, saved states, MIDI-note/velocity scans, round-robin and layer review | Partial on Windows x64 | The VST's Plugin Scanner discovers standard VST3 locations and can add a user-selected plugin folder to the scan, enumerate programs exposed by an instrument, and import a chosen `.vstpreset` in an isolated MagDrum helper. It can save either a selected program or preset as a named kit in the shared database, select that kit, configure note/velocity capture and scan it in an isolated worker. Captured samples are searchable in the VST; its Sample tools now show layer/round-robin candidates and save user-confirmed velocity ranges and take groups. Interacting with a plugin-specific editor still uses the separate instrument manager. Manual Cubase review remains pending. |
| Semantic MIDI import/export, event editor, ambiguity/fallback reports, GM/custom profiles and CSV profile import/export | Partial | The VST imports patterns with lengths inferred from MIDI files and exports patterns with selectable lengths from 1–16 bars, reports ambiguous/unmapped/out-of-range notes, edits saved GM/custom CSV profiles, and lets users add/remove tempo and time-signature events at any quarter-note beat. The sequencer can edit individual hit drum, articulation, velocity, beat position and duration, then compare the imported baseline with current edits (added/removed hits, metadata and pattern length). The event list is preserved in Cubase plug-in state and MIDI export; grid edits remove only hits on the selected 1/8, 1/16 or 1/32 grid and preserve off-grid hits with a status message directing the user to Edit hits. Sequencer playback now maps each semantic event through the selected profile without fallback; missing exact mappings are skipped and reported. |
| Multi-bar, meter-aware sequencer, editable velocity, tempo/signature metadata, preview and loop | Partial | The VST has sixteen selectable bars, 1/8, 1/16 and 1/32 step grids (up to 32 steps per bar), variable meter changes aligned to the selected grid, per-step velocity presets, editable tempo and meter events, and looping sample preview. When the DAW is stopped, Play uses the plugin's tempo-aware preview. During host playback, the audio callback schedules semantic hits against the host's PPQ position and BPM at sample offsets and wraps at the pattern length; the host tempo is authoritative for this mode. The editor keeps polling while host-synced so local preview playback resumes automatically after Cubase stops. The grid maps later time signatures into shorter or longer bar spans and MIDI export retains them. Core tests cover block boundaries, loop wrap, tempo-to-sample timing, and negative-position preroll. Manual Cubase Pro 15 transport and audio review remains pending. |
| Portable metadata archive import/export and folder sync | Implemented on Windows x64 | The Sample tools menu imports/exports version 1 archives and syncs version 2 device snapshots through a user-selected folder. Folder sync carries tag additions and removals, manual categories and MIDI profiles; add/remove operations match local samples by content hash and size. It never copies audio or local paths. Shared-core tests cover removal propagation and concurrent re-adds; Cubase UI validation remains pending. |

The VST cannot take ownership of Cubase's audio device. Any standalone action that currently opens or configures a device must use the DAW's playback/render callbacks or a separate worker instead. Discovery, program enumeration, preset/program loading and note scanning use separate MagDrum helpers, so third-party plugins are not loaded into Cubase by these workflows. Windows x64 is the first target for parity work; other plug-in formats must be rebuilt and reviewed after the Windows behavior settles. Plugin-specific editors remain in a separate MagDrum manager process.

## Windows x64 completion path

The completion target is the Windows VST3 inside Cubase Pro 15. Linux, macOS, ARM64, iOS preview work and classifier research are outside this critical path until requested. Track code work against the rows marked **Partial** above; rows already marked implemented do not need another release solely to reconfirm them.

1. **Finish the music-making loop:** sample selection and assignment, DR-660 pad order, per-pad sound controls, MIDI input, sequencer playback against Cubase transport, and reliable state save/restore when a project is closed and reopened.
2. **Close MIDI workflow gaps:** complete event editing, mapping/profile operations, import/export and tempo/meter behavior, including clear reports for notes that cannot be mapped.
3. **Review library and scanner workflows in Cubase:** verify sample comparison and source/kit access, plugin discovery, preset/program import and scan-result review. Plugin-specific vendor editors remain an explicitly documented separate-window boundary.
4. **Run the Cubase acceptance pass:** check the workflows above in Cubase Pro 15, record each defect against its checklist row, and fix defects before adding unrelated scope.
5. **Make a release only for a coherent acceptance milestone:** build the Windows x64 Release, run its existing checks once, package it, then publish and test that exact package. Keep Debug builds for iteration; do not make numbered releases for individual UI edits.

This ordering puts the playable instrument path first while preserving the requested standalone-to-VST parity goal. Each code change should name the parity row and observable acceptance result it closes.

**State-persistence verification:** editing the sequencer's base tempo updates the saved editor state immediately. User changes to sequencer state, pad samples, and per-pad gain/pan/tune notify the host that the project state changed; opening the editor does not mark the project modified. Project sample files decode on a worker during state restoration, their paths remain serializable while loading, and the active editor refreshes when restoration finishes without marking the project dirty. The Windows plugin smoke test round-trips the tempo, two-bar length, semantic hits, mapping profile and tempo/meter metadata, and resaves sample paths during restoration. Saving and reopening a real Cubase project remains part of the manual host pass.

## Windows development and installation loop

Work Windows x64 only until the Cubase Pro 15 experience is accepted. Do not spend iteration time on Linux or macOS packages unless requested.

For each focused code or UI change, use `Build-Windows-Plugin.ps1`. Its separate x64 Debug tree avoids Release link-time optimization, tests, packaging and installation. The script reuses `build/local-windows-dev-x64` so MSBuild can reuse compiled JUCE and MagDrum objects across days and test builds; the directory name stays stable across days and releases. It builds only the VST3 for plug-in-only edits; it also builds the standalone scanner helper on first use or after a shared/app source changes. On 2026-11-16, a controlled incremental rebuild of `PluginProcessor.cpp` plus VST3 relink completed in 10 seconds; the build log showed the app target was skipped. A prior rebuild of both plug-in source files took 13 seconds. These are incremental-edit timings, not clean-build estimates. The full .194 Windows x64 Release run took 5:53 for compile/link, 0:49 for tests, 0:03 for packaging and 0:02 for CMake configuration. Open that Debug bundle in Cubase only when host review is useful. Batch related changes by parity row; create a numbered release only when a complete acceptance slice is ready for Cubase review.

Group changes by parity row and observable Cubase result. Then run `Build-Windows.ps1 -BuildRevision <test-number>` once: it checks localization and installer safeguards, builds the optimized Release app and VST3, runs the Windows x64 tests, and produces the ZIP. Set the revision to the release tag and adjust `-Parallel` only when the machine is responsive. Keep one build active per CMake tree; if the tree is locked or reports access denied, do not start overlapping builds against it. The script accepts `-BuildDirectory build/<new-windows-x64-tree>` for a separate tree, with the expected cost of a cold build. `-SkipTests` is for a local package when test executables are not needed; it is not the release check. The publisher rejects a Windows archive whose VST3 version does not match its test tag. The installer preserves the replaced MagDrum bundle in backup and moves other MagDrum bundles out of JUCE's two standard scan roots; it leaves other vendors' plugins untouched.

Keep the next work tied to Cubase acceptance and the ordered partial rows above. Work first on the end-to-end playable path (scan/import sample → assign pad/layer → trigger from Cubase MIDI → save/reopen project), then on sequencer transport and MIDI round-trip, then on scanner/source comparison review. Use the cached Debug build and lightweight focused checks during implementation; run the full Release build, existing tests, packaging and publishing once for each coherent acceptance slice. When Cubase review is available, test that exact Release package and record only actionable defects against the relevant row. Linux and macOS builds remain deferred until requested.
